Issue: [#47 Embedded Bandcamp player on event listings, artist and band pages, and the discovery deck](https://github.com/natea/newenglandmusic/issues/47)

## Context

`MusicAct` (abstract; `Artist`, `Band`) has `bandcamp_url` (validated by `core/artists.py`'s `validate_bandcamp_url`) and `field_sources`. `core/artists.py`, PRODUCT.md, AGENTS.md and the artist-records spec say nothing is ever requested from Bandcamp. On 11 November 2026 the owner decided that fetching an act's page once to read its album or track ID, so the site can embed Bandcamp's player, is acceptable use, with no proxies; the rule is amended here.

An event's play buttons are built by `core/artist_previews.event_artist_previews` and baked into the event's stored HTML (`event.html`), with `core/js/artist_preview.js` opening the service's player below the row on a click, so that nothing loads from the service until then. The matching commands re-render an event's HTML when a link changes (`match_youtube_artists` reports "re-rendered N events"). Spotify, Apple Music and YouTube buttons come from `SpotifyArtistLink`, `AppleMusicArtistLink` and `YouTubeArtistLink`, keyed by the artist name on the event; an event's `EventPerformer` rows link it to `Artist` and `Band` records in billing order. Band and artist pages are built in `core/views/act_page.py` with `links_of`, and `core/templates/core/band.html`. `add-artist-link-hub-links` (its code is in the repository; its spec files await archiving) added `read_artist_link_hubs`, `link_hub_*` fields, the `HUBS` politeness pattern (robots.txt through `check_event_sources.robots_allows`, the honest user agent, hand-handled redirects) and a weekly step, and `add-act-csv-export` (also in the code) made `core/act_export.py` list every field in `ACT_COLUMNS` or `NOT_EXPORTED`.

**The discovery deck from #26 is not in the repository,** and no change for it is open. The issue puts Bandcamp last in the deck's order "unless the proposal decides otherwise"; this change can only fix the rule, not draw the deck.

## Goals / Non-Goals

**Goals:** keep a player ID per act, found once from the act's own page; show Bandcamp's own player on listings and act pages, loaded only on a click; never request Bandcamp on a page view; never overwrite an editor's value.
**Non-Goals:** scraping anything else; finding Bandcamp pages; proxies; choosing the "best" release; the deck itself.

## Decisions

**1. Fields on `MusicAct`.** `bandcamp_embed_kind` (choices `album`, `track`, blank), `bandcamp_embed_id` (a string of digits, validated, blank), `bandcamp_embed_status` (blank, `found`, `no_playable`, `blocked`, `gone`, `unreadable`, `failed`) and `bandcamp_embed_checked_at`, following the link-hub fields: on the abstract model, so Artist and Band share them, one migration, no backfill. A fifth field, `bandcamp_embed_for` (the Bandcamp URL the player was read from, set by the lookup), lets "address changed" be detected without a comparison against history. A player is *usable* when kind and ID are set and either an editor set it (marked "editor" in `field_sources["bandcamp_embed"]`, counting whatever the URL and whatever the status, which stays blank because it is read-only) or its status is `found` and `bandcamp_embed_for` equals the current `bandcamp_url`. Every display rule (listing button, band section, deck function) tests "usable", never the status alone. The ID is a string of digits rather than an integer so a longer ID can't overflow.

**2. The lookup, `core/bandcamp_embeds.py`.** `find_candidates(html, base_url)` returns music releases in page order as `(kind, id)`; `player_available(session, kind, id)` fetches the player's page; `apply(record, result)` returns the saved values. Reading by structure, with BeautifulSoup and `json`, no script run:
- redirect to a release: JSON-LD `@type` `MusicAlbum` whose `albumRelease` `item_id` gives the album ID; for a track page the `data-tralbum` / page properties (`item_type`, `id`);
- grid: `li[data-item-id]` where the value starts `album-` or `track-`, skipping any other prefix (merch tiles use `merch-`, to be confirmed against the fixtures);
- no music tile on the front page: the same host's `/music` once.
The 25-act experiment (11 redirecting to a release, 14 grids, 25 found) is the starting evidence; the first build task re-checks it on a different sample and saves sanitised pages as fixtures.

**3. "Not available" releases.** The release page doesn't say whether the player works, so the command asks for Bandcamp's player address of each candidate (one more request, two seconds later) and treats the "not available" player page as unplayable, trying at most three candidates, which bounds a run at one page, one `/music` page and three player checks per act. This is the cost of detecting physical-only releases; the markers on the player page that mean "unavailable" are recorded from fixtures in the first task.

**4. Politeness.** The honest user agent (`check_event_sources.USER_AGENT`), `robots_allows` imported from `check_event_sources` and cached per host for the run, a two-second pause, a timeout, redirects handled by hand and refused off `bandcamp.com` and its subdomains (a custom domain Bandcamp redirects to is refused too, status `failed`; see questions), no proxy and no JavaScript. 403, 406 and 429 are `blocked`; 404 and 410 `gone`. Three acts in a row `blocked` stop the run, so a block isn't pushed harder. The default pace is far below what a person browsing would make, and one lookup per act per year is the intended load.

**5. When to look up, in `due()`.** Never looked up; `found` after 365 days; the other statuses after 90 days; `bandcamp_embed_for` differing from `bandcamp_url`. For an act that already has a found player, every non-success outcome (403, 406, 429, 404, 410, a timeout, a 500, a robots refusal, an unreadable page) keeps the ID, kind, status `found` and `bandcamp_embed_for`, updates only the time checked and is reported in the run's problems, so a working player is never hidden by a failed refresh; the `blocked`/`gone`/`unreadable`/`failed` statuses apply only to acts with no found player. (A 404 on the act's page may mean the player is also gone; the owner may prefer to clear it, and the refresh interval question covers this.) `--limit` caps a run (at 100 when not given, like the Spotify and YouTube commands, since the first run has hundreds of acts at up to five requests each), `--refresh` ignores the schedule, `--dry-run` saves nothing. Writes use `queryset.update()` (as AGENTS.md prefers), then re-render the events of acts whose player changed, as `match_youtube_artists` does, because the button is baked into event HTML.

**5a. Re-rendering outside the command.** The button is baked into event HTML, so every change that alters it must re-render the act's upcoming events through `bake_event_html` / `Event.save`: `MusicActAdmin.save_model` when the kind, ID or `bandcamp_url` changed, and its delete and clear actions; the actions that toggle `needs_review` (`mark_ready`) and `import_act_list`; the rebuild of `EventPerformer` rows in `core/event_performers.py`; and deleting an act. One shared helper re-renders the events of a set of acts.

**6. Editor values.** `field_sources["bandcamp_embed"] = "editor"` when the admin form's changed data includes the kind or ID, set in `MusicActAdmin.save_model` as the existing marks are; the command skips such an act. Clearing both removes the mark. The import, enrichment and `clear_musicbrainz` don't touch these fields: they are not in `MUSICBRAINZ_FIELDS`, and the import and act-list loops only write the fields they own.

**7. Event listings.** `event_artist_previews` gains a `bandcamp` key per entry, from the event's performers: `EventPerformer` rows for approved, non-`needs_review` artists and bands with a usable player, matched into the entries by normalised name (an act that has Spotify matches shares its entry, so the Bandcamp button follows its Spotify, Apple Music and YouTube buttons; one with only Bandcamp gets its own entry at its billing position). `event_artist_previews` today returns an empty list at once unless Spotify, Apple Music or YouTube previews are enabled (`core/artist_previews.py`); that guard is dropped for Bandcamp, so the button shows on a site with none of them on. `event.html`'s `{% if artist_previews %}` and the click selector in `artist_preview.js` (which lists the Spotify, Apple Music and YouTube link classes) each gain a Bandcamp entry. Usable players only (decision 1). The button is the same kind of plain link as the others, with `data-bandcamp-kind` and `data-bandcamp-id`; `artist_preview.js` opens a `bandcamp.com/EmbeddedPlayer/<kind>=<id>/size=large/tracklist=true/artwork=small/` frame, Bandcamp's large player (about 300px tall, with artwork and track list, as chosen from the sketches), below the row on a click and closes any other open player. Only digits and a fixed kind reach the frame's address; nothing else from the record is used in it. The button is baked into the event's HTML, so it shows in the listing without a query per page view.

**8. Band and artist pages.** A "Listen on Bandcamp" section after the links, with a play button that swaps in the iframe on a click (the same script, so no Bandcamp request before then). The frame carries a `title`. Without JavaScript the section is a link to the page. A page must keep the content-security policy, if one is set, allowing `bandcamp.com` frames; build task 4.3 checks.

**9. The deck.** A single function in `core/artist_previews.py` returns an act's players for a given screen in that screen's order: events keep Spotify, Apple Music, YouTube, then Bandcamp; the deck's order, YouTube, Apple Music, Spotify, Bandcamp, is recorded as data for #26's change to call. Nothing draws the deck here.

**10. The rule, amended.** `core/artists.py`'s docstring, AGENTS.md ("Artists and bands", "Paid and rate-limited APIs", and the pipeline entry for `read_artist_link_hubs`, whose "weekly, last" and "never Bandcamp" wording becomes "weekly, before `find_bandcamp_embeds`" and "never requests Bandcamp") and PRODUCT.md are reworded to: Bandcamp is requested only by `find_bandcamp_embeds`, for an act's own page and player, to read a player ID; no scraping beyond that, no proxies. PRODUCTION.md doesn't hold the rule (a grep finds only import columns), so it only gets the command's documentation. The artist-records requirement is modified in this change. `add-artist-link-hub-links` modifies the same requirement, and the same change's weekly-jobs edit overlaps this one's; this change's text includes the link-hub source, so archive that change first (or merge the wording).

**11. CSV export.** The kind, ID and status are exported (`bandcamp_embed_kind`, `bandcamp_embed_id`, `bandcamp_embed_status`), after `bandcamp_url`, so an editor can see which acts have a player; the time and `bandcamp_embed_for` go in `NOT_EXPORTED` as bookkeeping, as `link_hub_checked_at` is. The export code is already in the repository, so this is not conditional, and `test_act_export` fails until the five fields are classified. The issue leaves this open, so it is also listed below.

**How each outside service is mocked.** Tests never touch the network. Bandcamp pages are recorded HTML in `core/tests/fixtures/bandcamp/` (a redirect-to-album page with JSON-LD, a track page, a discography grid, a merch-only front page with a `/music` page, a page with no releases, an "not available" player page and an available one), stripped of anything personal. Command tests patch `bandcamp_embeds.requests.Session` with a fake session, as `test_read_artist_link_hubs` does, returning a fixture, a robots.txt, a 404, a 429, a 500, a timeout or a redirect off Bandcamp, and counting requests so a test can assert that none was made (a recent lookup, an editor's player, a blocked page, a page view). The `robots_allows` import is patched where `check_event_sources` is, as the other commands do. The pause is patched out, and the schedule uses a frozen clock. Page and listing tests render with the stored player and assert there is no Bandcamp frame before a click; the click is tested in the Playwright browser test that already covers the play buttons, with the frame's address checked and no request made out to Bandcamp (the route is intercepted).

## Open Questions

- **Extra requests.** The owner approved fetching an act's page once. This design also asks for the `/music` page (when the front page has no music tile) and up to three player pages, so up to five requests an act, all at the two-second pace and only for acts with a Bandcamp URL. Is that within the acceptable use the owner approved, or should it fetch the page alone and skip the player check?
- **Pasted embed code.** An earlier owner note (add-artists-and-bands) had editors paste Bandcamp's embed code and the site keep only the digit ID. This design has editors enter kind and ID directly; accepting a pasted embed is left out. Should the admin also parse a pasted embed?

- **Does the deck exist yet?** Issue #26's deck isn't in the code. Bandcamp is last in its order, as the issue says, but should this change wait for the deck, or ship the order as data (decision 9) for the deck's change to use?
- **Order on the event row.** The issue gives the deck's order as YouTube, Apple Music, Spotify, Bandcamp; the event row today is Spotify, Apple Music, YouTube. This keeps each as it is and adds Bandcamp last. Should the two match?
- **Custom domains.** Many Bandcamp pages are on an act's own domain that Bandcamp serves; a stored `bandcamp_url` is always on `bandcamp.com` (validated), but a redirect to a custom domain is refused here. If the experiment's redirects included some, this should allow them when the target is a page of the same release.
- **Robots.txt.** The owner's decision covers fetching a page; this change still obeys robots.txt and records `blocked` for a disallowed page. If Bandcamp's robots.txt disallows the pages needed, is the owner content that the feature then finds nothing?
- **Refresh intervals.** 365 days for a found player and 90 for the other results are guesses. A release can also be removed or made unavailable later; the visitor then sees Bandcamp's own "not available" in the player. Is that acceptable, or should a refresh be more frequent?
- **Choosing the release.** The first playable release is used (the featured release on a redirecting page); the newest or most popular may be better. Left as it is, as the issue describes.
- **Track versus album players.** A track ID gives a single-track player; no look-up tries to find the album around it. Fine?
- **Player size on listings.** Decided: Bandcamp's large player, as in sketch B, because it is the closest match to how the other players open under a row. The cost is a tall row; the frame closes any other open player so the page doesn't grow without bound.
- **CSV export.** Which of the kind, ID and status belong in the export (decision 11).
- **Privacy.** A Bandcamp frame loaded after a click sets Bandcamp's cookies in the visitor's browser. The privacy page may need a line, as it may for Spotify and YouTube.
- **Content-security policy.** Whether the site sets one that would block `bandcamp.com` frames (task 4.3 checks).

## Risks / Trade-offs

- **[Custom domains refused]** Acts redirected to a custom domain are recorded `failed` and retried every 90 days, a request each (see the custom domains question).
- **[Browser test]** The Playwright test intercepts Bandcamp; its fixture must also block all other outbound network.

- **[Bandcamp changes its pages]** Structured data or tile markup may change. → Status `unreadable` is recorded, visible in the admin and the run's problems; fixtures document the shapes.
- **[Bandcamp blocks us]** → A three-in-a-row block stops the run; `blocked` is kept and retried after 90 days; the pace is well below browsing.
- **[A wrong player]** The first release may not be the act's best. → An editor can set or clear it.
- **[Removed releases]** A stored ID can stop being playable. → The player shows Bandcamp's own message; refresh yearly.
- **[Event HTML staleness]** The button is baked in. → The command re-renders the events of acts that changed.

## Migration Plan

Add the five fields with blank defaults (one migration, no backfill). The first weekly run is capped at 100 acts and looks up acts never looked up (all of those with a Bandcamp URL), about 5 requests an act at most, two seconds apart; run the first batch by hand with `--limit 25` and log it to `logs/find_bandcamp_embeds-YYYY-MM-DD.log`, then let the weekly job carry on. Roll back by dropping the fields and the button; nothing else depends on them.

## Sketches

The owner chose option B on the issue ("most closely consistent with the way the other players are implemented"). Two screens: an event listing with the Bandcamp button and its open player, and an artist or band page.

- [Option B: Full player with artwork](sketches/b.html). **Thesis:** Bandcamp's large player is the draw for small acts: artwork and track list open under the row, and a Listen section with a plum rule on act pages. **Risk:** A 300px player under a row breaks the dense list's rhythm, and opening several events makes the page very long.
