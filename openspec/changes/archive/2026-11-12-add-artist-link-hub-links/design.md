Issue: [#29 When adding pages for new artists, or when augmenting pages for existing artists, check for and extract linktr.ee or…](https://github.com/natea/newenglandmusic/issues/29)

## Context

`MusicAct` (abstract; `Artist`, `Band`) has `website`, `bandcamp_url`, `instagram_url` and `youtube_url`, and `field_sources` saying who set each ("import", "musicbrainz", "wikidata", "editor"). The import and enrichment never overwrite an editor's value, and `clear_musicbrainz` removes only values marked "musicbrainz" or "wikidata". `artist_enrichment.links()` reads MusicBrainz's URL relations but keeps only the homepage, Bandcamp, Wikidata, Discogs, Instagram and YouTube ones. `check_event_sources` already knows `linktr.ee` as a social domain for venues (`SOCIAL_DOMAINS`) and has `robots_allows`, the user agent `venue-db-event-check/1.0` and polite crawling. `act_page.links_of` builds the public page's links. Neither `enrich_artists_from_musicbrainz` nor `import_artists_from_events` is in `bin/daily.sh` or `bin/weekly.sh`; they are run by hand. Issue #29's thread settled that the site should read the hub page and use the links in it: fill gaps, flag conflicts, overwrite nothing.

## Goals / Non-Goals

**Goals:** keep a hub address per act; read it politely on the weekly schedule; fill empty link fields from it; surface disagreements for an editor.
**Non-Goals:** finding hubs by searching or guessing; storing other links; running JavaScript; changing venue checks.

## Decisions

**1. Where the address comes from.** Three sources, none of which guesses: the record's `website` when its host is a supported hub; any MusicBrainz URL relation on a hub host (`links()` gets a `link_hub_url` key, whatever the relation type: the `URL_TYPES` filter in `core/artist_enrichment.py` is widened so a hub link under any relation, such as "free streaming", is kept); an editor in the admin. `field_sources["link_hub_url"]` records which ("editor", "musicbrainz", or "import" for a copy from `website`); an editor's wins. A hub address in `website` stays there (the import, an editor or MusicBrainz put it there on purpose, and nothing is overwritten). The command copies it to `link_hub_url` (marked with the source of the website) before reading, so `due()` finds the record (it re-copies when the website changes while the stored address is still that copy's own, marked with the website's source; an editor's or MusicBrainz's address is never re-copied over); the website field and its `field_sources` entry are not touched. A real site found on the hub is then saved as a finding on `website` (current value: the hub address), which an editor can accept. A cheap pre-pass in the command, not enrichment, does the copy, so it works for records enrichment never visits.

**2. Fields on `MusicAct`.** `link_hub_url` (URL, blank), `link_hub_status` (choices: read, empty, unreadable, blocked, gone, failed, or blank for never read), `link_hub_checked_at`, and `link_hub_findings` (a JSON list: field, current value, hub value, seen-at, dismissed flag). A JSON list on the record, not a table: there are at most four findings per record, they are only read with the record, and `MusicAct` is abstract so a table would need an `Artist` and a `Band` foreign key as `EventPerformer` has. Dismissals are kept as entries with `dismissed: true` so a dismissed hub value is remembered. The new fields are not among `MUSICBRAINZ_FIELDS`, so clearing a MusicBrainz match leaves them alone (the filled links are marked "link hub", which `clear_musicbrainz` doesn't touch). `clear_musicbrainz` does drop every `field_sources` entry valued "musicbrainz", including `link_hub_url`'s; it is changed to keep that key, so the address stays marked as MusicBrainz's. Findings are plain data on the record and untouched. The stored address thus outlives the match it came from; that is intended, since it is still a page a person or MusicBrainz named, and an editor can clear it. Long values: `website` is limited to 200 characters, so `classify` rejects any link too long for its field (no fill, no finding) rather than failing the save.

**3. One module, `core/link_hubs.py`.** A `HUBS` table: name, hosts, and `readable` (True or False). First list, to be confirmed against each live page while building, so a host that turns out to need JavaScript is switched to address-only rather than dropped: Linktree (`linktr.ee`), Beacons (`beacons.ai`), Bio.link (`bio.link`), Lnk.Bio (`lnk.bio`), Linkin.bio (`linkin.bio`), Solo.to (`solo.to`), Hoo.be (`hoo.be`), AllMyLinks (`allmylinks.com`), Campsite (`campsite.bio`), Taplink (`taplink.cc`). Functions: `hub_for(url)` (the hub and whether the path names a page, not the home page or a reserved path), `fetch(session, url)`, `links_on(html)` returning `[(label, url)]`, `classify(links)`, and `apply(record, links)` which returns the changes and findings. Linktree and several others embed their links as JSON in the page (a `__NEXT_DATA__` script) as well as, sometimes, anchors; `links_on` reads both, with BeautifulSoup and `json`, and no script is run. Many hub links are wrapped in the hub's own click-tracking redirect; those aren't followed (the rule is no request to anything but the hub page), so they are ignored unless the embedded data gives the real address.

**3a. What the live pages showed (11 November 2026).** Only Linktree was checked; Nate set the other hubs aside until an act uses one ("i don't care about those other hubs right now. we'll check them when the time comes"), so their `readable` flags stay the first guess above. The first production dry run found 4 hubs due, all on Linktree, and recorded each as "blocked (robots.txt forbids it)". Linktree's robots.txt lists about fifty named crawlers and ends `User-agent: *` / `Disallow: /`, so the honest agent `venue-db-event-check/1.0` may not read it. Linktree has no public read API; its MCP server is OAuth-scoped to the owner's own profiles. Asked about scope, as task 1.1 said to, Nate chose that editors copy an act's Linktree links by hand from the hub address in the admin, with no other user agent and no reading around robots.txt, and that act pages show the hub link prominently (issue #52). Linktree stays in `HUBS` as readable: the job still asks its robots.txt once a run and records "blocked", so the admin shows why nothing was read, and reading starts on its own if Linktree ever allows the agent.

**4. Fetching.** A `requests` session, the honest user agent, `robots_allows` (imported from `check_event_sources`, not moved or copied: `fetch_events` and `match_eventbrite_organizers` import it and tests patch it there; the command caches each host's answer for the run, so a hub's robots.txt is fetched once, not once per record, and robots.txt itself may be redirected as `robots_allows` already does) and `check_event_sources.USER_AGENT` ("Mozilla/5.0 (compatible; venue-db-event-check/1.0)", which carries the honest token `venue-db-event-check/1.0`), a one-second pause, a timeout, `allow_redirects` handled by hand so a redirect off the hub host is refused (status "failed"). 403, 406 and 429 are "blocked", as for venues (Linktree may answer 403 to a plain client; task 1.1 checks that, and if every Linktree read would be "blocked" the scope is reconsidered with the owner); 404 and 410 "gone". The weekly cadence and one page per record keep it well under what gets a crawler blocked.

**5. Classification, deliberately conservative.** By host: Bandcamp (`is_bandcamp_url`, so the model's validator agrees), Instagram (`https`, a profile path, not a post or reel), YouTube (`/channel/`, `/@handle`, `/c/`, `/user/`; not `watch`, `playlist` or `youtu.be`). A website only from a link whose hub label says "website", "site", "homepage" or "official" and whose host isn't a hub, social, streaming or ticketing site; an unlabeled personal domain could be a shop, a label or a venue. Exactly one candidate fills; two or more for a field produce a finding and no fill, since which one is the act's own is the question.

**6. Filling and flagging (`apply`).** For each field: if the hub has no candidate, nothing (an existing finding for it is dropped; a value filled earlier stays). If the record's value is empty (or a hub address in `website`): set it, mark "link hub". If the record's value is marked "link hub" and the hub's differs: replace it. Otherwise, if the two are the same by the rule in the spec (host without `www.` and `m.`, path lower-cased without a trailing slash, no query): nothing. Otherwise save a finding unless the same hub value was dismissed. Nothing is ever applied over an editor's, the import's, MusicBrainz's or Wikidata's value. A hub address in `website` is not "empty": a real site on the hub becomes a finding. Replacing a value marked "link hub" is the one deliberate exception to "flag rather than overwrite": the site set that value itself, so a changed hub is the best evidence it is stale. Enrichment protects these fills too: `apply_details` and `add_introduction` in `core/artist_enrichment.py` currently skip only "editor" (and "musicbrainz") values, and would blank or replace a "link hub" one. They are changed to leave a "link hub" value alone when MusicBrainz or Wikidata has none, and to let MusicBrainz's or Wikidata's value replace it when they do (marking it theirs), as the risk table says. The two imports read the same marks: `artist_import._apply` (`core/artist_import.py`) skips any field whose source isn't "import", and `act_list.fill` (`core/act_list.py`) fills only unset fields or the list's own. Both are changed to treat a "link hub" owner like unset, so a CSV row's or a curated list's value replaces a hub fill and is marked "import" (or the list's key); otherwise a hub's guess would outrank the vetted sheet. In `apply_details` this covers two loops: the Instagram/YouTube one, and the website/Bandcamp one, which now also replaces a "link hub" value, not only an empty or "musicbrainz" one. Findings give an editor a reason to look; they don't say which side is right. A known false positive: a YouTube `@handle` and a `/channel/UC…` for the same channel differ by address, so they raise a finding; it costs an editor one click, and resolving handles would need the YouTube API.

**7. Admin.** A "Link hub" fieldset on `MusicActAdmin` (so for both kinds): the address (editable, validated by `hub_for`, `field_sources` marked "editor" by the existing `save_model`), status and time (read-only), the findings (read-only table), a list column with the number of open findings, a list filter, and two admin actions on the list, "Accept link-hub findings" and "Dismiss link-hub findings", since a custom per-row button needs a new view and no new screen is wanted. Accepting sets the field and marks it "editor".

**8. Schedule.** A new `RecordedCommand`, `read_artist_link_hubs`, in `bin/weekly.sh` after the venue steps (weekly: a hub page changes slowly and the weekly job already crawls). It reads the records a `due()` query returns (an address (after the pre-pass copy from `website`) and never read, or read over seven days ago), up to `--limit`, and sets `job_summary` to counts of read, filled, flagged and failed, and `job_problems` to blocked, gone and failed records. `JobRun.problems` entries are shaped for venues (`venue_id`, `sheet_id`, `name`, `problems`), so an act's entry is `{"venue_id": null, "sheet_id": "", "name": "<act name> (artist|band)", "problems": ["blocked"]}`. `problems_table` in `core/admin.py` builds a venue change link from `venue_id`, reads `sheet_id` and heads the table "venues with problems"; it is changed so an entry without a `venue_id` shows its name as plain text, with no link, and the heading reads "records with problems" when any entry is an act. Counts go in `job_summary`. The command and the admin actions write with `queryset.update()` (as AGENTS.md prefers), so an editor saving a record during the run isn't clobbered by a stale whole-record save; this skips `updated_at`'s auto-update, which nothing reads. `import_artists_from_events` and `import_artists` need no change: a new artist with a hub address is picked up by the next weekly run, and a new one without has nothing to read until enrichment or an editor gives it an address. Enrichment, still run by hand, therefore feeds this command only for records MusicBrainz knows.

**How each outside service is mocked.** Tests never touch the network. Hub pages are recorded as HTML in `core/tests/fixtures/link_hubs/` (a Linktree page with its embedded data, a Beacons-style page with anchors, one with scripted links only, one empty page), with any key or personal data stripped. The command tests patch `link_hubs.requests.Session`, as `test_check_event_sources` patches `check_event_sources.requests.Session`, with a fake session that returns the fixture, a robots.txt, a 404, a 429, a timeout or a redirect off the hub's host, and counts requests so a test can assert that none was made (a blocked page, a recent read, an address-only hub, Bandcamp). MusicBrainz is replayed with the existing `core/tests/musicbrainz_fixture.py`, with a hub relation added. The 7-day rule uses a frozen clock.

## Open Questions

- **Searching for hubs nobody linked.** The thread asks to "check for" hub pages when pages are added, and the proposal reads that as checking the sources the site already has. Looking up a handle from the act's name would find more, and more wrong ones (a different "Horse"). Is that wanted later, with an editor confirming each?
- **Reading the act's own website for a hub link.** Many acts link their Linktree from their site's header or footer. This would add one page request per record. Left out until the first runs show how many hubs the other three sources find.
- **Which hubs.** The list in decision 3 is a first guess from the best-known services; the issue says to research alternatives, and that is the first build task. Which of them can be read without JavaScript is not known until each live page is checked.
- **A website only when the hub labels it.** A stricter or looser rule is a judgement call; an editor can widen it from the findings' evidence after the first runs.
- **Other links on the hub** (Spotify, Apple Music, TikTok, Facebook, tickets, merch). The records have no fields for them, and Spotify's and Apple Music's terms limit how their links may be used to find music elsewhere. They are ignored for now.
- **Showing the hub address on the public page.** Not asked for in the issue, so left out. It would be one more "More links" entry in `links_of` (which would also stop a hub-only act getting the "missing links" invitation). Does the owner want it?
- **Hub discovery for new artists.** The issue asks for checks "during the regular workflow" when pages are added or augmented. Enrichment and the artist import run by hand, so a new artist gets a hub address only when someone runs enrichment (MusicBrainz knows it) or an editor types it; the weekly run only reads addresses already there. Should enrichment join the weekly job?
- **Replacing a hub-filled link.** A later read replaces a value the hub itself filled, as the one exception to "overwrite nothing". Does the owner want a finding there instead?
- **A link that disappears from the hub.** The proposal keeps what was filled. Should it be cleared instead, since a hub that dropped a link may mean the account is gone?

## Risks / Trade-offs

- **[Hubs block or break]** Some hubs may forbid crawlers in robots.txt, or rework their pages. → Status "blocked" or "unreadable" is recorded and visible in the admin; the address stays.
- **[A wrong hub address from MusicBrainz or a website field]** A namesake's page fills the wrong links. → The address comes only from sources a person or MusicBrainz's matching vetted; a fill only enters empty fields, is marked "link hub", and is replaced by anything an editor or MusicBrainz says.
- **[Noisy findings]** Equivalent addresses that look different raise findings. → The comparison ignores `www.`, `m.`, case, trailing slash and query; the handle-versus-channel case is accepted.
- **[Hub links are redirects]** Tracking wrappers hide the real address. → They are ignored rather than followed.

## Migration Plan

Add the four fields with blank defaults (one migration, no backfill). Existing records whose `website` is a hub address get `link_hub_url` from the command's pre-pass at its first run, before the `due()` query. Roll back by dropping the fields; filled links stay as plain values marked "link hub".
