Issue: [#36 Use the same header and nav menu on every page](https://github.com/natea/newenglandmusic/issues/36)

# Design

## Context

Read from the code: `core/templates/core/base.html` holds the masthead. Its `.rightColumn` shows "Saved shows" and the `MenuItem`s with `show_in_header`, joined by `|` characters. A `☰` link (`.burgerColumn`, an `<a href="javascript:;">`) calls an inline `toggleBurgerMenuContents()` that reveals `#burgerMenuContents`, a list of *all* menu items, hidden by inline `display:none`. Styles are in `core/static/core/scss/header.scss`; there is no media query, so the header links stay on one line on a phone and the ☰ shows at every width. Every page template extends `base.html`, so the masthead is already shared (`test_discover.py` checks home and Discover match). Menu items are the `MenuItem` model, edited in the admin; `0102` and `0104` add "Bands & artists" and "Discover bands" by migration.

On the listing, `index.html` includes `geo_filter_form.html` (state, metro, towns, neighborhoods, auto-submitting with a small inline script), then the `location_form` tag, then `calendar_subscribe.html`, which is already a `<details>`.

## Decisions

### 1. Menu form (settled in the thread)
Links across the top on a computer; a ☰ button on a phone; never both. One markup list rendered once, with CSS showing it as a row above a breakpoint and as a stacked column, opened by the button, below it. Rendering the list once guarantees the two forms are the same list. The breakpoint is 600px, matching the existing `band.scss` and `act_index.scss` queries.

### 2. One list
The hidden `#burgerMenuContents` list of all items is removed. The one menu uses the items marked "show in header", plus "Saved shows". Items that are only in the footer stay there. Items that today appear only in the hidden list (`show_in_header` false, which is the model default) are no longer reachable from the header. This is a decision nobody has made yet, so it is an open question below, and the build starts by checking the real menu items. The now-unused `get_all_menu_items` tag is deleted. "Saved shows" stays a fixed link added by the template, not a menu item, and keeps its `.saved-count` element so `saved_shows.js` still updates the count; the saved-shows requirement "The header shows a Saved shows link with a count" is unchanged and covered by a test.

### 3. The button
A `<button type="button">` with `aria-expanded`, `aria-controls` and an accessible name ("Menu"), replacing the `<a href="javascript:;">`. A small script toggles `aria-expanded`; the inline `toggleBurgerMenuContents` is deleted. Without JavaScript the list is simply always shown: a small script adds a `js` class to the page, and only under that class do the narrow-screen styles hide the list and show the button. So with scripts off, the button is not shown and every link is visible on every width (stacked on a phone). The script is a static file loaded with `defer`, like the other per-feature scripts in the head. To avoid a flash of the full link list on a phone before it collapses, the `js` class is set by a tiny inline snippet at the top of the head, before first paint; the deferred file handles the toggle only. The menu is a `<nav>` with a stable id `siteMenu`, which the consistency test and the updated tests use instead of the old regex. The `|` separators go, since they would be wrong in a stacked column; links are separated with spacing. "Saved shows" today comes first in the header; the menu puts it last, after the admin-ordered items, and this reorder is intended. Removing `#burgerMenuContents` also removes its 50px bottom margin, so the spacing between the header and the content (notably on pages with the month header) is checked and kept. The `.rightColumn :first-child` rule in `header.scss`, which hits every descendant first child, is replaced with a rule scoped to the nav.

### 4. Listing controls
The geo filter and the location form go into one `<details>` titled "Filters and location", closed by default and never opened by itself, with a one-line summary of what applies (state, metro, towns, saved location). The "show all" clear link, which `geo_filter_form.html` holds, is shown beside the summary line when a filter applies, so it is reachable without opening. The summary needs the saved location, which today `location_from_request` computes only inside the `location_form` tag (`core/templatetags/location_form.py`) and `index.html` cannot see; the listing view (`core/views/index.py`) puts the same `location_from_request` result in the template context for the summary, so the summary and the form always show the same place. The section is omitted when neither control renders (`geo_filter_form.html` renders nothing without state options; the location form is hidden until the census data is loaded), and when only one renders the title names only that one. The wrapper is built in `index.html` only: Discover (`discover.html` includes the same filter) and saved shows (which uses the location form) are unchanged and keep their open forms. The wrapper keeps the filter's inline auto-submit script adjacent to its form (it finds the form with `previousElementSibling`). The "use my location" button and the town chips (`location.js`, `town_chips.js`) work once the section is opened; the form is hidden, not removed. The location form's own behaviour (`event-distance`) and the subscribe box's (`area-calendar-feeds`) are untouched; only where they sit changes, so the subscribe box is no longer directly beside the filter. The subscribe box is already a `<details>` and stays one. The existing auto-submit script keeps working inside it. The `geo_filter` cookie behaviour is unchanged.

### 5. Consistency check
A test fetches a set of pages and compares the markup of the `nav#siteMenu` element, replacing the current regex that depends on the old ids. `core/templates/core/empty.html` does not extend the base template; the build confirms no view renders it (none was found) and the "every page" claim covers pages that extend `base.html`.

## Sketches

Three options for the menu and the folded listing controls, each showing the wide masthead, the listing's top, and the phone menu opened.

- [Option A: Quiet bars](sketches/a.html) — **Thesis:** Keep the masthead as is, with the links in one row beside the name. Fold the filters and location into one closed bar, with the subscribe box in a second closed bar below it. Each bar has a summary line. This is the smallest change and keeps the existing folding sections. **Risk:** Two stacked bars still take two lines before the first show, and the summary line can get long when many filters apply.
- [Option B: Chips and plum nav strip](sketches/b.html) — **Thesis:** Put the links in their own plum strip under the name and search box. On the listing, show the applied filters as visible chips with two buttons, Change filters and Subscribe, so what is filtering is readable at a glance. **Risk:** A taller masthead pushes the listing down, and the chip row adds new markup and a new open-and-close pattern beyond details elements.
- [Option C: Centered nav, one Refine bar](sketches/c.html) — **Thesis:** Centre the name with the links beneath it. Fold filters, location and subscribe into one Refine bar whose summary names what applies, with two buttons that open each panel. **Risk:** It departs most from the current masthead and needs two panels in one bar, so it needs script, and without JavaScript the panels must stay open.

## Testing
No outside service is called, and tests never touch the network. Server markup is checked with Django `TestCase`; the narrow and wide layouts, the button toggle and keyboard use with the existing Playwright setup (`core/tests/browser.py`, `requirements-dev.txt`) at two viewport sizes, with outbound requests blocked. Menu items are created as `MenuItem` rows directly, so the "main links" scenario tests the fixture's rows, not production data. Existing tests that touch the moved controls are updated: `test_location_browser.py` (opens the section first), `test_index_geo_filter.py`, `test_metro_towns.py`, `test_discover_filter.py` (unchanged markup there, checked) and the saved-shows tests.

## Open Questions
- **Which items does the one menu use?** Proposed: those marked "show in header", plus Saved shows, as the header shows today. The alternative is all items, which would put footer-only items in the header. Items only in the old hidden list drop out of the header under the proposal. The real menu items are checked before building (a read-only look in the admin), and the owner decides whether to flag any for the header.
- **Which menu items exist?** The issue lists events, venues, artists, listings, about and Discover. The code has "Bands & artists" and "Discover bands" by migration, and others are admin data. Should a migration add any missing ones (venues, listings, about), or are editors expected to? The proposal does not assume.
- **What is "the calendar picker"?** Taken here as the "Subscribe to this calendar" box only. The month-link row is not folded; if the picker means that row or the month grid, folding it needs a decision.
- **What is "advanced search"?** Taken here as the state, metro and town filter and the "near" form. The search box in the masthead is left as it is.
- **Should the section open by itself** when a filter is active? Proposed: no, it is always closed on load and the summary line shows what applies.
- **Which sketch?** Option A (Quiet bars) is chosen; B and C are rejected.
- **Discover and saved shows** keep their open forms: this is the proposal's reading of "on the listing page"; say if they should fold too.
- **Saved shows** is in the header today; kept in the menu unless told otherwise.
